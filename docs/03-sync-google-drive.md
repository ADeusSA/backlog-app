# 03 · Синхронизация с Google Диском

Пометка `⚠ verify` — проверить по актуальной документации Google перед реализацией; протокол от этого не зависит.

## 1. Цели и допущения

- Один пользователь, несколько ПК, **последовательное** использование (не одновременное редактирование). Задача — чтобы на любом ПК была актуальная база и картинки, и чтобы ничего не потерялось, если два ПК всё-таки изменили данные офлайн.
- Единица синхронизации — **снимок базы целиком** + **набор неизменяемых файлов изображений**. Построчное слияние — не в итерации 1 (задел: `updated_at`, `tombstones`, UUID).
- Пользователь видит файлы у себя на Диске в папке `Backlog/` и может скопировать их вручную.
- Работает офлайн: приложение никогда не блокируется отсутствием сети.
- **Ноль настроек у конечного пользователя.** Единственное действие — кнопка «Войти через Google» (в мастере первого запуска и в настройках). Учётные данные OAuth-клиента вшиты в сборку и общие для всех копий приложения; каждый вошедший пользователь получает собственную папку `Backlog/` на своём Диске. Владелец сборки настраивает проект Google Cloud один раз (§11), после чего приложение можно передавать другим людям как есть.

## 2. Google Cloud и OAuth

- Тип OAuth-клиента: **Desktop app**. Redirect — loopback `http://127.0.0.1:{port}` (порт выбирается свободный при каждом входе), **PKCE S256** обязателен; OOB и custom-URI-схемы Google больше не поддерживает. Для desktop-клиентов Google выдаёт `client_secret`; официальная документация: «the client secret is obviously not treated as a secret» → встраивание в приложение допустимо (подтверждено, research/02 §3a). Секрет показывается в консоли только при создании клиента — сохранить сразу.
- Scope: **`https://www.googleapis.com/auth/drive.file`** — приложение видит только созданные им файлы; scope non-sensitive, верификация приложения не требуется (подтверждено). Плюс `openid email` для показа адреса аккаунта в настройках. `drive.appdata` (скрытая папка, удаляется при отключении приложения) отвергнут: пользователь хочет видеть файлы.
- Проект Google Cloud заводит владелец приложения; в Google Auth Platform нажать **Publish app** (статус In production). Подтверждено: в статусе Testing refresh-токен живёт 7 дней и допускается ≤ 100 тест-пользователей; клиенты, неактивные 6 месяцев, удаляются; на аккаунт действует лимит 100 refresh-токенов на client_id. Экран согласия может показывать «непроверенное приложение» — задокументировать в README.
- Токены: `access_token` (в памяти), `refresh_token` — зашифрован `safeStorage.encryptString` (Windows DPAPI) и записан в `data/sync/token.bin` (документ 01 §10). Расшифровать может только этот пользователь Windows на этом ПК → при переносе папки на другой ПК потребуется повторный вход (ожидаемое поведение, показывается понятное сообщение). `client_id`/`client_secret` — в коде (`src/main/sync/google.config.ts`), в логи не попадают.
- Поток входа: «Подключить Google Диск» → main поднимает `node:http`-сервер на `127.0.0.1:0` (порт из `server.address()`) → `shell.openExternal(authUrl)` (системный браузер) → пользователь соглашается → редирект на loopback → код → обмен на токены `POST https://oauth2.googleapis.com/token` (глобальный `fetch`) → сохранить refresh → создать/найти папку `Backlog` → первичное согласование (§5.4). Таймаут ожидания 5 мин; страница-ответ в браузере: «Готово, можно закрыть вкладку» (HTML в стиле Aurora, одна строка).
- Выход: `POST https://oauth2.googleapis.com/revoke`, удаление `token.bin`, очистка `sync/state.json`; локальные данные не трогаются.

## 3. Структура на Диске

```
Backlog/                              (папка в корне «Мой диск»; id хранится в state)
├── manifest.json                     маркер актуальности; пишется ПОСЛЕДНИМ
├── backlog.db                        последний снимок (VACUUM INTO), без WAL
├── images/
│   └── <uuid>.webp | .png            плоско, имя = images.id + расширение (неизменяемые)
└── history/
    └── backlog-2026-09-07T12-31-05Z-r1532-<device>.db   предыдущие снимки (хранить последние 10)
```

`manifest.json`:
```json
{
  "format": 1,
  "schemaVersion": 2,
  "revision": 1532,
  "deviceId": "018f…",
  "deviceName": "DESKTOP-BARMIN",
  "updatedAt": "2026-09-07T12:31:05.120Z",
  "db": { "fileId": "1AbC…", "sha256": "…", "sizeBytes": 8421376 },
  "images": { "count": 812, "totalBytes": 61234567 },
  "appVersion": "1.0.0"
}
```
Те же `revision`, `deviceId`, `sha256` дублируются в `appProperties` файла `backlog.db` (`⚠ verify` лимит 124 байта на пару) — для быстрой проверки без чтения манифеста.

Локально `data/sync/state.json`:
```json
{
  "folderId": "…", "manifestFileId": "…", "dbFileId": "…",
  "base": { "revision": 1500, "sha256": "…", "updatedAt": "…" },   // удалённое состояние на момент последней успешной синхронизации
  "lastPushedRevision": 1500, "lastPullAt": "…", "lastPushAt": "…",
  "remoteImages": ["<id>.webp", …],                                    // кеш листинга images/ (обновляется при push/pull)
  "pendingImageDeletes": ["<id>.webp"]
}
```

## 4. Определения

- `L` — локальная ревизия (`meta.db_revision`), `B` — `state.base.revision` (что мы последний раз видели/записали в облако), `R` — ревизия из удалённого манифеста.
- Локальные изменения есть ⇔ `L > lastPushedRevision`.
- Удалённые изменения есть ⇔ `R ≠ B` (обычно `R > B`; при откате из истории может быть меньше — трактуется как «изменения есть»).

## 5. Протокол

### 5.1 Pull (при запуске и по кнопке)
1. Нет сети / не подключено → состояние `offline`/`disabled`, продолжаем локально.
2. Скачать `manifest.json` (≤ 2 КБ). Если `schemaVersion` > известной приложению → диалог «Обновите приложение», база не подменяется, синхронизация приостанавливается.
3. `R == B` → облако не менялось. Если `L > lastPushedRevision` → запланировать push. Готово.
4. `R ≠ B` и **нет** локальных изменений → **скачать** `backlog.db` во временный файл `sync/incoming.db` → проверить `sha256` = манифесту → открыть read-only и `PRAGMA integrity_check` → закрыть текущую БД → сохранить локальную копию в `backups/pre-pull-<ts>.db` → атомарно заменить (`fs.rename` на том же томе) → удалить `-wal/-shm` → открыть → `PRAGMA wal_checkpoint` → `state.base = R`, `lastPushedRevision = L(новая)` → скачать недостающие картинки (§5.3) → событие `dbReplaced` (UI полностью перезагружает данные, текущий экран сохраняется по маршруту).
5. `R ≠ B` и **есть** локальные изменения → **конфликт** (§6).

### 5.2 Push (отложенно, по таймеру, при выходе, по кнопке)
Планировщик: любая запись → таймер 60 с (сбрасывается новыми записями), но не реже, чем `интервал` из настроек (5/15/30 мин, по умолчанию 15) при непрерывной работе; при закрытии окна — немедленно; кнопка — немедленно. Один push за раз (мьютекс); если push идёт, новые изменения ждут следующего цикла.
1. Скачать манифест; если `R ≠ B` → это конфликт (кто-то писал параллельно) → §6, push отменяется.
2. `db.pragma('wal_checkpoint(TRUNCATE)')` → `VACUUM INTO 'sync/outgoing.db'` (файл предварительно удалён; альтернатива — `db.backup()`) → `sha256` (`node:crypto`).
3. Картинки: `diff = local images − state.remoteImages` → загрузить недостающие (multipart, до 4 параллельно, ≤ 5 МБ каждая); `pendingImageDeletes` → удалить на Диске.
4. Предыдущий удалённый `backlog.db` → **копия в `history/`** (Drive `files.copy` в папку history с новым именем) — до перезаписи.
5. Загрузить `outgoing.db` поверх существующего `backlog.db` (`files.update`, resumable upload при > 5 МБ, `appProperties` обновить). Если `dbFileId` ещё нет — `files.create`.
6. Записать `manifest.json` (`files.update` содержимого) — **последним**: только после этого облако считается обновлённым.
7. `state.base = {revision: L, sha256}`, `lastPushedRevision = L`, `remoteImages += uploaded`, очистить `pendingImageDeletes`, обрезать `history/` до 10 файлов.
8. Любая ошибка на шагах 2–6 → состояние `error` с текстом, повтор с экспоненциальным бэкоффом (1, 2, 5, 15 мин), манифест не трогаем — облако остаётся консистентным (старая пара db+manifest).

### 5.3 Изображения
- Имена файлов на Диске = `images.id + ext`; файлы неизменяемы (новая картинка = новый id), поэтому сравнение — по именам, без хешей.
- При pull: `remote listing − local files` → скачать (до 4 параллельно). Листинг папки `images/` делается `files.list` с `pageSize=1000` и `fields=files(id,name)`; кэшируется в `state.remoteImages`.
- Отсутствующая локально картинка в UI показывает плейсхолдер `dominant_color` до докачки; UI не блокируется.
- Удаление картинки локально → `tombstones(image)` → `pendingImageDeletes`.

### 5.4 Первичное согласование (подключение аккаунта)
- Облако пустое, локальная база есть → push.
- Облако есть, локальная база «пустая» (только сид, `L` ≤ сидовой ревизии) → pull без вопросов.
- Обе непустые → диалог с двумя карточками: «Локальная: 120 игр, изменена 7 сен 12:00» / «В облаке: 118 игр, изменена 5 сен, ПК DESKTOP-OLD» → «Использовать локальную (облачная уйдёт в history)» / «Использовать облачную (локальная сохранится в backups)».

## 6. Конфликты

Ситуация: `R ≠ B` и `L > lastPushedRevision` (оба менялись). Приложение **никогда** не решает само.

Диалог (модальный, стекло, документ 04): заголовок «Данные изменились на двух устройствах», две карточки с фактами (устройство, время, число игр, ревизия, размер) и кнопки:
1. **«Оставить эту (локальную)»** — облачная версия копируется в `history/` (она там уже будет по шагу 5.2.4), затем push.
2. **«Взять из облака»** — локальная сохраняется в `backups/conflict-<ts>.db`, затем pull.
3. **«Решить позже»** — синхронизация в состоянии `conflict` (индикатор жёлтый), приложение работает локально; напоминание при следующем запуске.

В итерации 2 — «Сравнить»: таблица различий по сущностям (по `updated_at`/tombstones) с ручным выбором; для этого уже сейчас все таблицы имеют `updated_at`, а удаления — tombstones.

## 7. Целостность и безопасность данных

- Никогда не синхронизировать живой файл БД: только снимок `VACUUM INTO` после checkpoint; `-wal`/`-shm` не загружаются.
- Перед каждой подменой базы — локальный бэкап; `backups/` хранит 10 последних + бэкапы `pre-pull`/`conflict` (не удаляются автоматически, показываются в настройках).
- Скачанный файл проверяется `sha256` и `PRAGMA integrity_check` **до** подмены; провал → файл удаляется, ошибка в UI, локальная база нетронута.
- Замена файла — атомарная (`fs.rename` на одном томе) при закрытом соединении; все prepared statements пересоздаются после открытия.
- Один push/pull одновременно; при закрытии приложения ждём завершения (документ 05 §1).
- Токены — `safeStorage` (DPAPI) в `token.bin`; в `state.json` — только идентификаторы файлов.
- Квоты Drive API (в quota units: 325 000/мин на пользователя; get = 5, list = 100, download = 200, update = 50) для одного пользователя не достигаются даже при первичной загрузке 800 картинок; при 403 `rateLimitExceeded`/429 — экспоненциальный бэкофф с учётом `Retry-After`; параллельность ≤ 4.

## 9. Абстракция провайдера (задел)

```ts
interface SyncProvider {
  id: 'gdrive' | 'folder';           // 'folder' — обычная папка (например, в OneDrive/Яндекс.Диске) — итерация 2
  connect(): Promise<AccountInfo>; disconnect(): Promise<void>;
  readManifest(): Promise<Manifest | null>;
  downloadDb(dest: string): Promise<void>; uploadDb(src: string, manifest: Manifest): Promise<void>;
  listImages(): Promise<string[]>; uploadImage(name: string, src: string): Promise<void>;
  downloadImage(name: string, dest: string): Promise<void>; deleteImage(name: string): Promise<void>;
  copyDbToHistory(name: string): Promise<void>; pruneHistory(keep: number): Promise<void>;
}
```
Движок (`engine.ts`) реализует §5–6 поверх интерфейса; Google Drive — первая реализация (`drive.ts`, Drive API v3: `files.list/get/create/update/copy/delete`, `alt=media`, multipart и resumable upload).

## 10. Критерии приёмки

1. Два ПК (или две папки с разными `device_id`): изменение на A → закрытие → запуск B → данные и картинки идентичны (сравнение `sha256` снимков после checkpoint и списков файлов).
2. Офлайн-правки на обоих → конфликт обнаружен на втором, оба варианта выбора не теряют ни одну версию (history/backups).
3. Обрыв сети во время push после загрузки db, но до манифеста → облако остаётся консистентным (старая пара), следующий push завершает работу.
4. Скачанный повреждённый файл (подменить байты) → отклонён, локальная база не тронута, ошибка понятна.
5. Токен отозван в аккаунте Google → состояние `error` с предложением переподключить, без падения.
6. Закрытие приложения при `pending` → данные в облаке обновлены; при принудительном убийстве процесса — при следующем запуске push выполняется.
7. 800 картинок первичной загрузки на ПК B — прогресс отображается, UI отзывчив, плейсхолдеры заменяются по мере докачки.
8. Человек с другим Google-аккаунтом запускает ту же сборку: кнопка «Войти через Google» → согласие → папка `Backlog/` создана на его Диске, состояние `synced`; ни одного поля для ключей в приложении нет.

## 11. Одноразовая настройка Google Cloud (делает владелец сборки, ~15 минут)

Результат: `client_id` и `client_secret`, которые кладутся в `src/main/sync/google.config.ts` и попадают в сборку. Делается один раз; конечные пользователи ничего из этого не видят.

1. Открыть [console.cloud.google.com](https://console.cloud.google.com) → создать проект `Backlog`.
2. **APIs & Services → Library** → включить **Google Drive API**.
3. **Google Auth Platform → Branding**: название приложения «Backlog», support e-mail, логотип (опционально; при загрузке логотипа Google может потребовать верификацию бренда — `⚠ verify`, поэтому в первый раз логотип не загружать), контактный e-mail разработчика.
4. **Google Auth Platform → Audience**: тип **External**; нажать **Publish app** (статус In production). Верификация не требуется, пока используются только non-sensitive scopes; при статусе Testing refresh-токены живут 7 дней и допускается ≤ 100 тест-пользователей — поэтому Testing не подходит.
5. **Google Auth Platform → Data access**: добавить scopes `https://www.googleapis.com/auth/drive.file`, `openid`, `email` (все non-sensitive) → сохранить.
6. **Google Auth Platform → Clients → Create client**: тип **Desktop app**, имя `Backlog Desktop`. Сразу скопировать **Client ID** и **Client secret** — секрет показывается только один раз при создании.
7. Вписать значения в `src/main/sync/google.config.ts`:
   ```ts
   export const GOOGLE_OAUTH = {
     clientId: '…apps.googleusercontent.com',
     clientSecret: '…',            // для Desktop-клиентов не считается секретом (см. §2)
     scopes: ['https://www.googleapis.com/auth/drive.file', 'openid', 'email'],
   } as const;
   ```
8. Проверить сценарий A17 (документ 10 §4) на аккаунте, отличном от аккаунта владельца проекта.

Что важно помнить:
- Клиенты, неактивные 6 месяцев, Google удаляет (восстановление 30 дней) — обычное использование приложения поддерживает активность.
- Если позже добавить sensitive/restricted scopes (например, полный `drive`), потребуется верификация Google — не добавлять.
- При публикации консоль может попросить ссылки на домашнюю страницу и политику конфиденциальности — допустимо указать README репозитория и короткую страницу политики (данные хранятся только на Диске пользователя) (`⚠ verify` при настройке).
- Экран согласия показывает название приложения и запрошенные разрешения («Просмотр и управление файлами Google Диска, созданными этим приложением», «Просмотр адреса электронной почты»). Это ожидаемо и описано в README для пользователей.
